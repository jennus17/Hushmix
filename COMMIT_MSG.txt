fix: keep the window matched to its content across monitors; verify update checksums

Reported: the window deformed when moved between the 1080p and 4K monitors, the
"Mixer Disconnected" banner appeared over a connected mixer, and update downloads
could not be verified. Each is fixed below, with the root causes rather than
symptoms.

WINDOW DEFORMATION ACROSS MONITORS
Three separate mechanisms were fighting over the size of the window; measurements
on a real move between a 1920x1080 (100%) and a 2560x1600 (175%) monitor:

1. Content scaled x1.73 while the frame grew x2.64, and the size never returned
   to baseline (600x500 instead of 387x332). Two causes:
   * ``CTk.geometry()`` multiplies its argument by the window scaling, so a
     request for "670x573" reached Tk as "1172x1002" while the unscaled number
     was recorded as the cached size - and ``CTk._update_dimensions_event`` then
     recorded the scaled size, so ``_set_scaling`` derived a wrong base and
     pinned the window through minsize/maxsize.
   * the window never followed its content at all: it stayed at CustomTkinter's
     600x500 default, and the correction compared a scaled window size against
     an unscaled content request, so it never triggered.
2. ``ScalingTracker.update_scaling_callbacks_for_window`` multiplies the detected
   monitor DPI into every widget, so calling ``set_widget_scaling(1.75)`` on a
   175% monitor produced widget scaling 3.06 - the factor applied twice. Widget
   scaling is now left entirely to CustomTkinter, which does it correctly.
3. Correcting the size from ``<Configure>`` fed itself: every ``geometry()`` fires
   another ``<Configure>``, the queue stopped draining and the application froze
   as soon as the window reached the second monitor. An ``after_idle`` callback
   was also dispatched re-entrantly from inside ``update_idletasks()``.

The arrangement now: CustomTkinter's tracker keeps scaling the widgets, its
window-scaling callback is replaced with one that updates its own factors but
never touches the geometry, and ``WindowManager`` sizes the window to the frame's
requested size with a converging loop (bounded passes, a minimum interval, and
re-entrancy collapsing).

Measured after the fix, twice each way: 387x332 -> 670x573 -> 387x332 ->
670x573, window always equal to content, size restored exactly on return.

"MIXER DISCONNECTED" OVER A CONNECTED MIXER
* CustomTkinter's rescale calls ``_set_dimensions`` on every widget and
  ``CTkLabel`` re-grids itself, so a *hidden* banner reappeared - which the
  DPI-triggered refresh made routine. It also meant the window was fitted while
  the banner was still gridded, which is where the last 44 px (banner height
  x 1.75) of mismatch came from.
* ``update_connection_status`` is now idempotent and re-applied on ``<Configure>``
  before the size is measured, so the banner is truthful whatever rebuilt the
  layout.

UPDATE VERIFICATION
* ``_parse_github_response`` now looks for a published checksum: a
  ``Hushmix.exe.sha256`` asset (or ``.sha256sum``/``.checksum``) is downloaded,
  and a ``SHA256: <hash>`` line in the release notes is used as a fallback. The
  custom-server response is normalised the same way.
* ``verify_download`` verifies exactly when a checksum exists, and *logs a
  warning* when it does not, instead of silently accepting an executable header -
  a truncated or substituted download used to pass.
* Added ``build_tools/make_checksum.py``; ``build_tools/build.py`` now writes
  ``dist/Hushmix.exe.sha256`` and prints the line to paste into release notes.
* ``check_now`` / the "Check now" button and the ``last_update_check`` guard came
  with the earlier update work; this commit only extends verification.

TESTS
* ``tests/test_dpi_scaling.py`` (28 checks) moves the real window onto each
  monitor when more than one is present and asserts the window equals its content
  at every step, that the size returns exactly to baseline, that the second
  monitor is repeatable, that five DPI polls do not drift the widget scaling
  (the double-application symptom), and that the banner stays truthful across a
  DPI change.
* ``tests/test_updater.py`` extended to 42 checks (51 with ``--download``):
  checksum extraction from asset/notes/custom responses, case handling, exact
  verification of the built executable against its sidecar, and rejection of a
  tampered binary.
* ``tests/smoke_fixes.py`` also asserts the settings window can reach the update
  manager.

VERIFIED
* Full suite green: 104 core, 48 profiles/lanes/filter, 42 updater (51 with a
  real 68 MB download), 35 GUI pipeline, 28 DPI, 22 fix regressions, 30 live GUI
  interactions, consistency checks.
* ``dist/Hushmix.exe`` rebuilt at 0.4.7 with a generated
  ``dist/Hushmix.exe.sha256``.

CAVEATS
* The executable could not be launched for a final confirmation: Windows Smart
  App Control (verified state 1) blocks the unsigned binary and Code Integrity
  logs "did not meet the Enterprise signing level requirements". Earlier builds
  did launch, so this is a machine policy rather than a build fault; distributing
  the application needs a code-signing certificate. This is now documented in the
  README.
* The live release (v0.4.6) publishes no checksum, so the updater logs the
  header-only warning for it. Uploading the generated sidecar makes verification
  exact from the next release onward.
