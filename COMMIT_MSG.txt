fix: stop profiles bleeding together, let content follow DPI, and harden updates

Reported symptoms were profile settings appearing to move between profiles or
vanish, the window growing without its content when dragged to a 4K monitor, a
spurious "Mixer Disconnected" banner over a connected mixer, and uncertainty
about whether updates still work. Each had a distinct cause.

PROFILE DATA LOSS AND MIXING
- on_profile_change published the new profile name immediately but deferred the
  actual data load by one event-loop turn, so for that turn the active profile
  said "new" while the channel data still belonged to "old".
- _collect_profile_state - which runs on every save - read the current profile
  back out of the *dropdown widget*, so a save landing in that window wrote the
  outgoing profile's entries into the incoming profile's slot, and vice versa.
  Reproduced: editing "Alpha", then switching to "Profile 1", left
  Profile 1 holding Alpha's applications.
- Switching is now atomic and synchronous: the outgoing profile is saved under
  its own explicit name, the incoming data is loaded, the name is published, and
  saves are suppressed for the duration (ProfileManager._switching). The
  dropdown is an output only and is never consulted when saving.
- save_profile() takes the profile name as a parameter instead of asking the
  widget which profile is active.
- ProfileManager no longer guesses list lengths: it uses the same VAR_FIELDS map
  as the GUI, so channels and buttons cannot be truncated on a switch.
- Verified: three profiles through repeated round trips, rapid switching,
  edit-then-switch-immediately, and deletion of both selected and unselected
  profiles.

"current" LANE HIJACKING A NAMED APPLICATION
- With App 1 = firefox and App 2 = current, both lanes wrote to the focused
  application, so two sliders fought over it. Focusing Firefox with the current
  lane active now does nothing, exactly as requested.
- AudioController.resolve_lanes() resolves every lane against one focused-window
  reading per packet; a lane naming an application explicitly owns it.
  Matching ignores case and the .exe suffix, a comma-separated entry owns each
  of its applications, and master/mic/system are never treated as process names.
- VolumeManager applies the per-packet resolution so the rule holds on the
  hardware path as well as the mute path.

WINDOW SCALING ACROSS MONITORS
- CustomTkinter already owns this: creating the CTk root sets per-monitor DPI
  awareness and ScalingTracker polls the window DPI every 100 ms, rescaling
  widgets and the window. The application fought it by setting `tk scaling`
  itself on <Configure> and rebuilding the GUI: the window was resized from the
  scaled dimensions while widgets were rebuilt at the old scale, which is why it
  grew without its content keeping up. CTk's own source notes that non-client
  scaling "does not work with resizable(False, False)" - the manual approach was
  never going to be correct.
- Removed every manual scaling call: the SetProcessDpiAwareness and
  `tk scaling` in HushmixApp, WindowManager.apply_dpi_scaling and its
  <Configure> hook, BaseWindow._apply_dpi_scaling, and the main window's
  DPIManager bootstrap. utils/dpi_manager.py is now a documented no-op shim.
- Measured at scale 1.75: window request 387x332 -> 670x617 and the channel
  fields 30 -> 52 px, i.e. the window and its content move together, and both
  return exactly to baseline at 1.0.

"MIXER DISCONNECTED" WHILE CONNECTED
- CustomTkinter's rescale calls _set_dimensions on every widget, and CTkLabel
  re-grids itself in the process - so a hidden banner reappeared over a
  connected mixer every time the window changed monitor. The DPI-triggered GUI
  rebuild above is what made it visible.
- update_connection_status() is now idempotent and WindowManager re-applies it
  on <Configure>, so the banner is truthful whatever rebuilt the layout.
- _layout_footer no longer grids the banner and leaves it for later.

UPDATES
- install_update ran `taskkill /f /im Hushmix.exe` while waiting for the old
  instance to exit. The script had already started the replacement by then, so
  the kill matched the new process too and could terminate the application it
  had just launched. The wait is now by process id.
- Settings are flushed before the process is replaced, so an update cannot lose
  channel names or button modes that had not been written yet.
- Added "Check now" to the settings window, so updates are reachable when
  automatic checking is off.
- The checker now respects last_update_check, so restarting the app repeatedly
  no longer hits the API on every launch.

TESTS
- tests/test_profiles_and_filter.py - 48 checks: profile isolation across
  switches and deletion, switch atomicity, lane ownership, and the signal
  filter (none need Tk or audio hardware).
- tests/test_dpi_scaling.py - 23 checks: window and content scale together at
  1.75 and return to baseline, the banner stays truthful through scaling
  changes and refreshes, and the "Check now" wiring.
- tests/test_updater.py - 37 checks (28 offline, 9 with --download): the PE
  version matches version.py, the live GitHub lookup, malformed responses,
  verification rules, the generated install script, and a real download of the
  published asset (68 MB, progress monotonic to 100%, cancel cleans up).
- tests/smoke_fixes.py extended to assert the settings window can reach the
  update manager.

VERIFIED
- Full suite green: 104 core, 48 profiles/lanes/filter, 35 GUI pipeline,
  28 updater, 23 DPI, 22 fix regressions, 30 live GUI interactions,
  consistency checks.
- The download path was exercised end to end against the real v0.4.6 release
  asset, and dist/Hushmix.exe was rebuilt and launched.

CAVEATS
- The monitor move itself was not performed: this machine's monitors are
  currently both at 100%, so scaling was driven through CustomTkinter's own
  public scaling API, which is the same path a DPI change takes.
- The install-and-swap step is inspected as generated script text, never run.
- Published releases carry no checksum, so verification can only confirm a
  plausible Windows executable rather than exact bytes. Publishing a SHA-256
  alongside the asset would make verify_download() exact.
